Native profile (perf, kernel.perf_event_paranoid = 1)
=====================================================

How: bench/perf.sh. Each benchmark runs a fixed number of ops (--ops, no
digest work), plain on core 3 and LeJIT on core 5 at the same time, under
prlimit --as=4000000000, with perf record -F 2000 --call-graph fp:
  stats 60,000 msgs; stats_quiet 1,500,000 msgs; controller 100,000
  requests; runner 2,000,000 msgs.
stats_quiet is the what-if: each matcher_by_type matcher has its
logger.debug f-string removed. Its output digest is the same as stats.
bench/perfsplit.py sorts self samples into the categories below. LeJIT's
code shows up in perf as dso "[JIT] tid <pid>": these are the anonymous
rwx mappings from lejit/src/platform.c:psyco_allocate_executable_buffer.
One 1 MB region of that mapping holds over 90% of the JIT samples in every
run. Setup (loading the pool, imports) is under 5% of each run.
CPython 3.10 is built without frame pointers, so call stacks from fp are
poor; I used --call-graph dwarf for stats_quiet only (for inclusive
costs). DWARF unwinding can't get through JIT code, which has no CFI.

Notes per benchmark
- stats: 64-65% of cycles turn the message into text (dtoa for floats:
  _Py_dg_dtoa, diff, quorem, multadd, Balloc; unicode_repr, dict_repr,
  PyObject_Repr), plus most of alloc/free and libc memmove. That's the
  debug f-string. LeJIT's own code is 3.4% of the run. Nothing to compile.
- controller: under LeJIT, 11.7% is still in the eval loop. That's the
  coroutines it won't compile (get_work, ControllerServer.run, datapool
  checkout, the _yield generator). Compiled code is 12.7%. The rest is C:
  sets/dicts (get_active, get_total_work), msgpack, random.
- runner: GC is about 15% in both modes (gc_collect_main 10.7%: every
  journey allocates a task, frames, a Context and dicts, which triggers
  gen-0 collections). msgpack pack is 11%. LeJIT compiles only 5.2%; the
  journeys, _execute, transaction() and Runner._run are coroutines or
  generators and stay interpreted.

So: compiled code and LeJIT helpers make up 22%, interpreted generators
12.5%, and C object work (msgpack, dict, hash, tuple, alloc, compare)
roughly 55-60%. Boxing floats is negligible (0.7%). As the checked build
showed, there's very little float maths in this path.

What LeJIT would need to get well past 1.33x here
- Compile generators, or at least inline a simple generator (one loop,
  yield of a tuple) into the `for` loop that consumes it, as it already
  does for generator expressions. That removes the ~12.5% of frame create,
  eval and free work. It also lets the yielded (key, value) tuple stay
  virtual, which saves part of the tuple alloc/free and RichCompare.
- Inline dict.get with a str constant key (the hash is known at compile
  time) instead of calling cimpl_dict_get_impl, and inline the
  `x in (const tuple of str)` test as pointer-equality checks first.
- Even with all of that, the C object work stays: about 55-60% of
  today's LeJIT time. That makes the ceiling about 2x over plain for this
  code. Going further would need the data to change, not the JIT: decode
  each message once and share it, intern or cache label strings so
  hashing is paid once, and dispatch on msg["type"] once instead of
  running 32 matchers per message.

Can LeJIT's code be symbolised cheaply for perf?
------------------------------------------------
Yes, it's feasible and cheap. perf already labels LeJIT's code
"[JIT] tid <pid>", which means it looks for /tmp/perf-<pid>.map: a text
file of "START SIZE name" lines in hex, which it reads at report time. All
of LeJIT's code comes from psyco_new_code_buffer (codemanager.c) inside
the rwx regions from platform.c, so one fprintf, gated by an environment
variable, when a buffer is closed (start, size, and co_name:firstlineno
of the code being compiled) would do it. Two caveats:
- Freed buffers get reused, so stale entries can overlap; you'd get the
  name of the last code compiled at that address.
- The file has to be in /tmp.
perf's jitdump format (perf inject --jit) would give per-buffer names and
code bytes, but needs more work. I haven't changed LeJIT.
